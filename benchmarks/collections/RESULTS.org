#+title: Collection lowering: JVM measurements, 2026-10-31

* Assessment

The consolidation is defensible as a compiler/semantics change, not a general
runtime speedup. Flat lowered mapv remains close to an explicit CPS loop.
Native doseq trades more compilation work and bytecode for lower observed
immediate-callback allocation. Nested collection code becomes smaller.
The tiny forked-inference fixture is dominated by the execution/inference
substrate; these measurements do not establish an inference speed advantage.

All six worker receipts, expected case counts and frozen harness hashes were
checked. See README.org for the protocol and results/2026-10-31 for raw data.

  pinned JVM measurements. No ClojureScript performance claim is made.

* Compilation and code size

Bytecode compilation below is Clojure eval/definition, not JIT machine-code
generation. Lowering is timed separately. A small shared instrumentation agent
counts actual defined class byte arrays without writing class files.

| Form | Lowering, baseline/candidate ms | Bytecode compilation, baseline/candidate ms | Classes | Class bytes |
|------+--------------------------------+--------------------------------------------+---------+-------------|
| Flat mapv | 0.309 / 0.339 | 1.617 / 1.626 | 16 / 16 | 25,330 / 25,476 |
| doseq | 0.494 / 0.885 | 2.385 / 4.100 | 24 / 36 | 33,581 / 54,593 |
| Nested mapv, depth 4 | 1.055 / 1.041 | 4.517 / 3.994 | 46 / 40 | 75,977 / 64,699 |
| Nested mapv, depth 8 | 2.727 / 2.512 | 7.557 / 6.285 | 86 / 72 | 154,457 / 121,227 |

The depth-8 case has 21.5% fewer class bytes and 14 fewer classes. Its paired
bytecode-compilation ratio is 0.861. Conversely, native doseq's class bytes
increase 62.6%; its paired bytecode-compilation ratio is 1.719. Native expansion
is more complete and chunk-aware, but it is not a free compilation optimization.

Straight-line awaits expose an existing scaling issue in both revisions:

| Await sites | Classes, both | Baseline class bytes | Maximum baseline class filename length |
|-------------+---------------+----------------------+----------------------------------------|
| 8 | 52 | 95,780 | 219 |
| 32 | 196 | 449,104 | 627 |
| 96 | 580 | 2,083,302 | 1,911 |

The transformed AST and class count grow approximately linearly in this
fixture, while deeply nested generated names inflate total bytecode size.
Both revisions compile through ordinary eval, but class-file export succeeds
at 8 sites and fails at 32 and 96 with IOException: File name too long.
This is a real export/AOT concern, not a new collection-pass regression.
It is not a universal site-count bound: the anonymous factory shape and
namespace/name lengths matter. aot_probe.clj reproduces this independently.

* Immediate callbacks

These are complete collection operations over 1,024 values, including task
construction/entry, callback execution and result consumption. Allocations are
JVM-wide Java heap bytes, not retained heap.

| Form | Baseline/candidate microseconds | Baseline/candidate allocated bytes |
|------+--------------------------------+------------------------------------|
| Native transient-based mapv | 12.02 / 11.51 | 27,321 / 27,321 |
| Native persistent vector loop | 26.19 / 27.23 | 195,418 / 195,418 |
| Pure mapv inside a CPS scope | 13.06 / 13.23 | 28,129 / 28,249 |
| Lowered effectful mapv | 52.08 / 55.14 | 278,123 / 278,244 |
| Explicit CPS vector loop | 52.19 / 55.45 | 278,123 / 278,244 |
| Effectful doseq | 40.38 / 43.68 | 169,451 / 138,851 |

Lowered mapv and the handwritten CPS loop allocate essentially the same amount.
At 16 values, observed doseq allocation falls from 4,688 to 2,440 bytes; at
1,024 values it falls about 18%. Candidate doseq did not satisfy the warm-up
stability criterion, so its displayed timing is exploratory.

The native persistent control shows why comparing only against ordinary mapv
would conflate continuation overhead with persistent-versus-transient building.
Pure host collection processing mostly retains its native bulk cost; entering
a resumable scope still has a fixed cost. Per-element suspension and persistent
accumulation are material costs for tiny scalar operations.

* Deferred callbacks

Each item is scheduled for a later executor turn; there is no artificial IO
delay. At 256 values, lowered mapv takes approximately 76.5 / 77.6 microseconds.
Its paired time ratio is 0.993, which provides no compelling speedup claim.
Allocated bytes are 262,615 / 283,152, but the explicit CPS loop changes by
almost the same amount: 258,455 / 279,056. The control-adjusted allocation ratio
is approximately 0.999. These results should not be described as an allocation
regression caused specifically by mapv lowering.

The development pilot demonstrated why caller-thread-only allocation was
misleading: about 1.4 KB on the caller versus about 19 KB JVM-wide for a
16-value deferred operation. Final measurements retain both counters.

* Forked inference

The fixture writes each choice into a managed atom and forces resampling at
all four observation barriers. Root creation, result validation/consumption and
cleanup are included. At 256 particles, medians are roughly 123--136 ms before
and 125--134 ms after, depending on model shape. Paired time ratios range from
0.981 to 1.038; observed allocation stays near 234 MB per complete run, changing
by less than 0.2%. This is allocated traffic, not retained memory, and forced
resampling plus world/state management make this a deliberately demanding
fixture. It is not a cost estimate for ordinary default SMC or a large simulator.

Late JIT activity remains significant in several inference samples. There is
no demonstrated inference speed advantage from this compiler consolidation.
The allocation scale also shows that collection-loop bookkeeping is not the
main optimization target in this particular world-forking workload.

Every measured run checks caller isolation, four barriers/resamplings, and
agreement between particle output and particle-local state. Separate checks
enumerate all 16 latent assignments for each of the three model forms on both
revisions: values, isolation and exact joint-score/evidence accounting pass all
48 paths per revision. This validates the fixture, not arbitrary inference code.

* Interpretation limits and additional controls

58/120 immediate cases, 40/48 deferred cases and 19/36 inference cases satisfied
the bounded warm-up heuristic. JIT activity occurred in samples from 1, 6 and
22 cases respectively. These are exploratory measurements with three process
pairs; neither small timing differences nor the heuristic constitute a proof
of a settled plateau or a confidence interval.

There is a conspicuous unchanged-control anomaly: the 1,024-element scalar CPS
loop shows 169 KB versus 251 KB allocated in the isolated workers. A separate
REPL comparison verifies alpha-equivalent generated CPS forms, including
compiler-relevant type metadata. Within that same JVM, the reference and
candidate compilers still produce different allocation counts; independently
compiling the identical candidate body also gives differing counts under JIT
warm-up. The raw anomaly is retained, not discarded. It is evidence that
optimization context matters and is not localized to the collection rewrite.
It prevents a blanket claim of runtime neutrality, as well as a blanket claim
of a source-level allocation regression. Per-case fork isolation/JIT profiling
would be the appropriate next measurement if this scalar fold becomes a target.

The conclusions supported most directly are the code-size trade-off, the
observed doseq allocation reduction, preservation of the handwritten-loop
cost profile for mapv, and the lack of an established inference speedup.
